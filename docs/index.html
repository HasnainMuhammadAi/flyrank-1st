Predicting and Ranking Declining Content Pages

A decision-support system for prioritizing which web pages a content team should review first — built, tested, and honestly corrected.

Dataset FlyRank ML Internship warehouse (79M rows) + starter sample (30K rows) Method Hand-written baseline vs. Random Forest Status Decision-support, non-production
00

Abstract

This paper presents a method for identifying and ranking web pages at risk of declining search performance, intended to support content teams who don't have time to review every page individually. The method compares a simple hand-written scoring rule against a trained AI model, evaluated fairly on data from clients the model had never seen, with a follow-up audit to catch and remove any unintended shortcuts. That audit revealed the AI model's initial results (a 56% jump over baseline) had been partly inflated; once corrected, the model still outperformed the baseline, but by a smaller, more defensible margin of about 12%. This work is observational and decision-support only — it identifies pages worth reviewing, but does not prove that acting on them will cause performance to improve. The result is a ranked action playbook with clear reasons for each flagged page, explicit rules for human review, and firm limits on what should never be automated.

01

Introduction & Problem Statement

Research question: to predict which pages are not performing well, and arrange them in order from worst performance first to best.

Decision this supports: an SEO/content manager who oversees a client's website and can't manually check every page uses this ranked list to identify the worst-performing pages first, then works on improving those pages.

Cost of getting it wrong: this system can fail in two directions. Flagging a fine page wastes the manager's limited review time — inconvenient, but recoverable. Missing a genuinely declining page is more serious, since the client's real traffic keeps dropping silently until someone eventually notices — directly affecting the client's business, not just the reviewer's time.

Why not June 2026 (the newest month available)? June is the last month in this dataset — there is no later month to check what actually happened afterward. A trustworthy "did this page decline?" label requires comparing an earlier period to a later one, so June cannot be used to build reliable training labels. May was chosen instead as a safe, mid-panel month with real data both before and after it.

Exclusions: AI-referral session data (sessions_ai and related columns) was excluded from feature-building — only ~30,000 of 79 million rows have any AI session activity, too sparse to model reliably.

Public-safety note All identifiers are pseudonymized hash codes (client_hash_id, content_hash_id). No client names, raw URLs, domains, or private queries appear anywhere in this data or this paper.
03

Methodology

Assumptions. This project assumes trend_direction == "down" (a currently-observed trend) is a reasonable proxy for whether a page's traffic will actually decline in the future — true future outcomes aren't directly measurable in this data. It also assumes 91+ days without an update is a meaningful staleness threshold, though this signal was only MIXED evidence: strong for well-populated buckets, less reliable at the thin, extreme end.

Label definition. is_declining, defined as trend_direction == "down" — a proxy for whether a page's traffic is currently trending downward.

Features used. ctr, avg_position, days_since_last_update, word_count. impressions_90d was excluded after a leakage check (below) found it likely overlapped in time with the label's own calculation window.

Baseline. A simple hand-written rule: +1 point if a page's CTR was meaningfully below the average CTR of other pages at the same position tier, +1 point if it hadn't been updated in 91+ days. Pages scoring 2 (both problems) were ranked highest.

Model. A Random Forest classifier — chosen because prior evidence from the starter pipeline showed it consistently outperforming simpler methods (logistic regression, decision tree) on this type of data.

Validation design. A client_holdout split — entire clients were placed either fully in training or fully in testing, never split between the two. This tests the model on genuinely new clients it has never seen, preventing it from memorizing client-specific quirks.

Leakage check. impressions_90d was tested by comparing model performance with vs. without it. See the correction below.

Correction on record · Week 6 audit
Precision@50, with impressions_90d: 0.780 → 0.560, without it

Removing this single feature dropped performance by 0.220 — strong evidence it had timing overlap with the label and was inflating the original result. It was permanently removed from the final feature set.

05

Limitations & Honest Framing

  1. Leakage risk. One feature (impressions_90d) likely overlapped in time with the label. Removing it dropped Precision@50 from 0.780 to 0.560 — part of the model's original apparent skill was not genuine.
  2. Small sample sizes. Some buckets used in this analysis (e.g. a freshness tier with only 174 pages) produced unstable percentages that could easily be due to chance rather than a real pattern.
  3. Data quality concerns. Many top-ranked pages shared the exact same "days since last update" value (104 days) — unlikely to be a real coincidence, more likely a placeholder or collection quirk. Staleness-based conclusions should be treated with added caution.
  4. Limited tracking coverage. Only about 6.3% of rows in the warehouse dataset had GA4 session tracking available. Any "zero" values in session-based fields may reflect missing tracking, not genuinely zero activity.
  5. Observational, not causal. This work cannot claim that refreshing a flagged page will cause its performance to improve — that would require an actual controlled experiment, which this data does not provide.

Intended use. This ranked list helps a content reviewer decide which pages to look at first — it suggests and ranks, but never decides or acts on its own.

Human review required Every flagged page needs human review before action, with extra caution for: pages under 300 impressions_90d (about 39% of all flagged pages, where the numbers can be noise), and pages where missing GA4 tracking may be mistaken for genuinely low activity.
This system should never be used to
  • Automatically publish, delete, or edit a page without human review.
  • Claim that refreshing a page will cause recovery — that requires a controlled experiment.
  • Treat any single flagged page as a certain, confirmed problem.

Monitoring & retrain triggers. (1) Re-check Precision@50 periodically — retrain if it falls below ~0.50; (2) repeat the leakage audit whenever new features are added; (3) recheck GA4 tracking coverage for drift over time.
